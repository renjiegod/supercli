# PR 人工审核机制（首期）

不启用自动审核、自动批准或自动合并。GitHub 承载投稿与评论，维护者在本地审核与预览。

## 投稿人

Fork 后编辑 data/catalog.json；写清官方文档、用途、安装方式与图标来源。没有公开仓库的 CLI 也可以投稿，不编造 Star 数据。个人内部脚本先标记为本地工具，公开前确认没有敏感信息。

## 维护者审核

1. 阅读 PR 的用途与官方来源。核对是否为真实 CLI，避免网页、SDK、同名镜像、失效链接。
2. `gh pr checkout <编号>` 到独立 worktree，检查 diff；不直接执行投稿里的安装脚本。
3. 核对厂商图标、许可证与官方安装文档；有条件时在隔离环境安装 / 执行无副作用的 --help、--version。记录实际验证范围，未试跑不声称已验证。
4. 手动运行 `pnpm check`、`pnpm build`，运行 `pnpm dev` 在页面检查搜索、分类、排序、详情和窄屏。
5. 在 PR 留下“通过 / 需修改”结论，说明证据与限制。确认通过后由维护者手动合并，禁止自动合并。
6. 合并 main 后由 Actions 自动构建、部署并验证线上提交；失败时检查工作流日志，修复后手动重跑。PR 审核与合并仍由维护者决定。

- 官方来源与名称：
- 安装命令来源 / 实测环境：
- 图标原始来源：
- 本地类型检查 / 数据检查 / 浏览器检查：
- 敏感信息检查：
- 结论：通过 / 需修改

## 数据更新

维护者在本地运行 `pnpm sync`，检查快照差异再提交。GitHub / GitLab 以外的 CLI 无可比 Star 数据，展示“未计分”，排在有指标条目后；绝不填 0 冒充已查询结果。

## 社区投稿收尾

按 [社区维护流程](COMMUNITY.md) 核对 `data/community.json` 收录时间、出处及推荐者的署名选择。信息修改不刷新旧收录时间；已合并但未上线不得提前标“已收录”。Issue 表单先由 GitHub 登录，不接本站 OAuth。
